Why test is larger than train

By design. Test is a benchmark: every test document meets every test attack, so results can be broken down by attack type and position. Train is a sample of 20 attacks per document. Train still has more documents.

Why the build differs from the briefs

Decisions and deviations

P1BIPIA clean and split3 notes
  • Split as the brief says: official test documents plus 126 tables moved from train (210 test tables), about 10% of each scenario held out for validation. The 11 emails present in both official splits are dropped from train.
  • "Language Translation" is a type name in both the train and test attacks, but train means "translate this phrase" and test means "answer in another language"; no string is shared. Kept; test metrics should be reported per attack group.
  • middle_index follows the brief's boundary for 869 of 879 documents; 10 use a fallback boundary.
P2Attacked samples4 notes
  • Code query: Fix the bug in my code. Error: <last line of the error field>. The brief says to find the error in the context, but only 9 of 100 Stack Overflow answers contain it.
  • Insertion joins pieces with one newline, as BIPIA does. P4 uses the same function, so the extra blank line is in both classes and is no shortcut.
  • Test uses the first question; train and validation draw one at random (177 documents have several).
  • Samples per document, as the brief says: test = every document × every test attack; train and validation = 20 sampled attacks per document. That is why test (21,550 attacked samples) is larger than train (9,740).
P3Harmless text pool10 decisions
ChangeWhy
Pilot of 7 email, 7 table, 6 code documentsA random draw gave 17 tables, 1 email and 2 code
Structured output for codeThe first pilot split sentence and code into two strings (97.7% rejected) and broke the JSON (300 texts lost)
Code wording rules narrowed86 ordinary code texts were wrongly rejected ("ensure that…", model.eval())
Judge prompt based on the dataset's own policyv1 caught only 30 of 40 real attacks; v2 rejected requests to an email's human recipient
Positive control in every runA judge that always says "no" would pass every benign text. Result: 40 of 40 flagged
Hybrid judge: email/table 20 per call, code 1 per callEmail/table agreed 100% with one-per-call; code only 97%. Judge cost about $34 → $12
Size cap and top-up from set-aside textsAn exact 7/7/6 mix left pools unfilled; 59 full-run pools were 1–2 short
2 approved short pools (17 and 18 texts)A urllib answer: natural additions use network code, which the brief forbids
Test email/table pools extended to 2525 attacked samples per pool with 20 texts produced identical twins
No Shieldstral 4-bit checkNo GPU on the build machine
P4Harmless twins3 notes
  • Least used text first, then the length window (the brief puts the window first). Window first gave 6,436 duplicate twins in test; now every pool text is used at most once and there are no duplicates.
  • Accepted trade-off: 83.6% of pairs are within the length window; the median gap is 5 characters. Pairs outside are mostly long test attacks and are flagged length_matched: false. Pairing by length rank and a word-based P3 prompt were tested and not adopted.
  • Twins carry no attack columns; parent_id links each twin to its attacked sample.
P5Nemotron (separate work)4 notes
  • Document = the first two levels of the matched path, serialised as JSON; the twin cuts the injection out.
  • At most 20 pairs per attacker goal (one legal goal had 148 records).
  • 11 sentence repairs (brief: 12) and 25 hard negatives (brief: 23); every cut point and hard negative was inspected.
  • 20 random pairs read in full: all correct.
